## Live attempt and limitation

The v8 attempt used the existing local Cardano deployment, its Gateway and
Hermes `1.13.2+adbe63e8`, plus a separate Cosmos container/data home and relayer
configuration. Initial fixture problems were corrected: regular governance
voting must exceed the SDK's default expedited period, readiness must include
committed blocks and published endpoints, and genesis must have a fresh time
to avoid immediately expiring the Cardano-side Tendermint client.

An initial attempt created Cosmos client `08-cardano-probabilistic-0` on
`upgrade-v8-1`, Cardano client `07-tendermint-1`, and Cardano connection
`connection-2` in its initial handshake state. It stopped on the stale genesis
timestamp, before a channel or transfer completed.

After the genesis fix, the retry on `upgrade-v8-2` created Cardano client
`07-tendermint-2` in transaction
`4583c09460f1a5f2548ddf80dc968ac6ab4a6cb142492a0081668f6a5bc26a0b`, included at
Cardano height `3348`. The Gateway never accepted this checkpoint during the
attempt. It reported:


The existing heartbeat process also reported an already-spent input while

## Conclusion

This implementation and the passing published-module tests require **no new
light-client module release**. They establish the control case of replacing a
host executable while retaining the same verifier and client store. They do
not establish packet-level compatibility for this local deployment, a changed
verifier/schema, an Injective binary, or the pending production release. The
live fixture must pass on a functioning, matching Cardano/Gateway/relayer stack
before the full #629/#603 compatibility gate can be considered satisfied.
