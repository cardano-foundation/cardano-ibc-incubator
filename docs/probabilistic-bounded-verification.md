A client with 4,000 pool records used to write about two megabytes even when it only needed to set its frozen height. At the captured Injective write charge of 30 gas per value byte, the post-proposal client exceeded the 75 million transaction gas limit before any other work. A two-observation challenge also repeated the original Cardano bodies and verified the original observation again.

The sole supported storage format keeps the public `ClientState` and `ConsensusState` small. The client carries its current verification generation and checkpoint reference. A checkpoint holds the slot, block hash, nonce accumulators and references to the registration, stake, credit, production, certificate-counter, settled-history and packet state. These objects live in the destination application's authenticated store. They are included in module genesis export. Restart and state sync do not depend on an external state service.

The maps use immutable pages of at most 4 KiB. A directory points to its children. An update copies the pages whose records changed and shares the rest with historical checkpoints. Page hashes bind the encoding version, record kind and network configuration. Each operation loads the records it uses rather than expanding the whole registry. A stake row contains a binary pool ID and a `uint64` amount. The sealed table retains its checked total. Settlement credit keeps exact fractions. Production records carry their observation epoch so advancing an epoch does not rewrite every pool's bitmap.

The settlement policy is unchanged. A producer needs the authenticated registration and effective VRF binding, six months of age and production in one of the five preceding completed epochs. Its distinct-producer credit remains `min(current_share, reference_share + 0.005)`. Credit is never renormalized. The rolling reference advances once per epoch using capped credit. Production in full bridge bodies and committed anchors is retained. Temporary descendants do not become saved production history or replace the anchor's nonce and certificate counters.

Native eligibility requires positive stake in the block's own epoch. A registered pool with recent production can regain stake after an epoch with zero stake. Its valid next-epoch descendant contributes no qualified pool or credit under the anchor's earlier table. It does not invalidate the other settlement evidence. An absent row represents zero stake for this qualification check. A malformed stored row or a missing snapshot page remains an error.

Verification runs through bounded `ObservationChunk` messages inside ordinary `MsgUpdateClient` transactions. Begin pins a specific checkpoint and policy. Table appends enforce canonical order, unique identities, complete row count and a checked total. Credit is calculated in bounded batches. Block appends authenticate native headers and full bodies through the anchor. Large certificate collections continue in separate steps. Completion checks the full observation digest and settlement thresholds. The final activation writes only the anchor's state. Speculative pages cannot supply packet proofs or become the base of an unrelated update.

Begin also commits a reverse hash chain over the complete ordered stake rows and block evidence. Each append supplies the commitment to the remaining suffix in `evidence_digest`. The destination checks that segment before saving rows, pages or progress. Any signer may relay a matching segment. Table segments must contain the next 128 rows or all remaining rows when fewer remain. This fixes their boundaries using the committed row count. Block segments may contain a smaller authentic prefix. Hermes resumes from the committed cursor. A different partial allocation or block history cannot poison another submitter's session. A live session cannot be discarded. Unfinished uploads from the older staged format must start a new session with the new commitments. Already committed checkpoints and receipts keep their meaning.

Every completed observation creates an immutable receipt. A normal challenge names the original receipt and verifies the alternative against that receipt's saved checkpoint. It then submits two receipt references. The conflict check compares settled anchors and their authenticated ancestry. Different temporary tails or unsigned allocations alone are not grounds for freezing. Isolated verification remains available for observations that were not admitted as forward updates.

A retained receipt authorizes queries for its exact base checkpoint through `receipt_id`, including the paginated verification records. The namespace and verification generation must match. Ordinary checkpoint retention can expire without removing this access. Restart discovery checks receipt anchors against the client's settled ancestry rather than requiring the old checkpoint's height index. An active alternative pins its original receipt. Completion transfers that dependency to the alternative's receipt so session cleanup cannot race the final challenge. Retention indexes remain discoverable while these dependencies are live and are released after the dependent evidence expires.

Sessions are public and have no signer owner. `ObservationDiscard` can delete a session only at or after its fixed 24-hour expiry. Permissionless cleanup follows the same expiry rule for the current verification generation. Neither path can erase an active challenger's progress or release its snapshot references. Authorized recovery can still discard sessions from an older generation.

The frequently written client is limited to 4 KiB. A consensus record is limited to 1 KiB. Verification and maintenance reserve 10 million gas for transaction admission and surrounding SDK work. Their own work may consume at most 26 million gas. The engineering target for simulation and execution is 36 million per transaction. With the public profile's `1.8` multiplier that requests 64.8 million gas. Complete signed transactions target at most 900,000 bytes under the captured one-million-byte relayer setting. Inline storage version `0` has been removed. The wire marker remains `2` and every other value is rejected. It is not a configuration choice.

The logical observation still supports 128 headers, including at most 97 full bodies of up to 96 KiB. Each block append processes at most four headers. Hermes uses one full body per transaction. Tables and credit use batches of 128 records with a shorter final batch. Certificate processing uses batches of 128 certificates with a shorter final batch. A body contains at most 3,072 certificates. There are at most 4,096 steps in an observation. Exact retries leave the sequence unchanged. Repeated completion at a new sequence number fails without consuming a step. Credit and body continuations also reject attempts after their work is finished. Retained registration capacity is 65,536 identities, independently of the 4,000-row election-table limit. An operation that exceeds its work budget fails without installing its speculative state.

A verified future table without Mithril certification starts a twelve-hour response window when it is activated. It does not immediately advance the trusted checkpoint or publish a root. This window budgets 4,096 steps at ten seconds per inclusion plus thirty minutes for detection and preparation. It is an explicit supported timing assumption rather than a measured guarantee of public-chain inclusion. Activation rejects proposals whose complete response window would extend beyond the client's trusting period. Matching retries and unfinished challenges do not reset the deadline. Host continuity advances a shared observation clock only across consecutive blocks with timestamp gaps of at most ten seconds. Only an uncertified stake submission records a twelve-hour target on that clock. Interrupted intervals do not count toward an unfinished window. They do not restart its elapsed time or create a host-wide pause. Certified allocations and allocations whose window has completed remain usable after a halt. The observation clock and each pending target survive restart and export/import. The published wall-clock deadline is the earliest cutoff. An uncertified pending table must also complete its recorded observation-clock target before activation. Committing an anchor requires every epoch allocation used by its bridge, anchor and settlement descendants to pass the same usability gate as proofs. An old-epoch anchor with following-epoch descendants must wait for the following epoch's cutoff too. Both commitment and proof use require a completed host block after the cutoff.

If a verified Mithril certificate arrives during the window and matches that exact installed table, the remaining stake wait ends at the certificate transaction's host time. The pending observation-clock target is removed. The public deadline, pending proposal and proof index move to the certificate cutoff together, including when a halt pushed the actual wait past its original wall-clock deadline. Historical receipts keep their original bytes. Commitment and proofs still require a completed host block after the certificate cutoff. Contradicting certificates freeze the client. Bootstrap requires Mithril certification and starts no twelve-hour window. Authorized recovery adopts an already usable substitute and starts no new stake challenge. Recovery rechecks the substitute's relevant epoch gates at preparation and activation.

Every permitted segmentation fits that budget. The two 4,000-row tables require at most 32 uploads and 32 credit continuations. Even one block per transaction requires only 128 block appends. Each of the 97 full bodies can require 23 further certificate continuations after its first 128 certificates. Including begin, completion and both activation transactions gives at most 2,427 transactions. A challenge needs only one freeze transaction after completion instead of two activations, so its bound is 2,426 transactions. At ten seconds per inclusion plus thirty minutes of preparation that is 7 hours 14 minutes 20 seconds. Rejected operations and retries cannot use up another submitter's session sequence. The timing assumption still requires the honest transactions to be included within the supported interval.

Authorized recovery pins the replacement objects before changing state. A bounded continuation compares certificate counters when needed. Activation advances the verification generation and writes small records. Proof and verification paths reject discarded generations immediately. Their bytes can remain until bounded maintenance releases their owners and removes unused pages. Current checkpoints, historical verification bases, receipts and unfinished sessions retain ownership of their referenced objects. No recovery transaction deletes the entire historical database. The settled hash index still grows with committed history, although it retains hashes rather than bodies or ledger balances.

Final recovery activation also reads the substitute's current authenticated client record. A later freeze or a change of verification generation invalidates the prepared replacement. The subject stays frozen and requires a fresh authorized recovery request. Normal forward progress in the same healthy generation preserves the pinned snapshot. Recovery still uses that snapshot rather than silently adopting the substitute's newer checkpoint. The source record is bounded by the existing 4 KiB client limit. Tests freeze the substitute with verified conflicting signed history after two counter batches commit. They also cover the substitute completing a separate recovery and an ordinary forward update that leaves the original pin usable.

A new authorized recovery may replace an unfinished preparation whose counter checks fail or whose replacement expires. It resets the scan and replaces the old preparation's pin owners. Permissionless continuation cannot choose that replacement. The subject stays frozen until all checks succeed. Activation rechecks checkpoint freshness and requires enough remaining lifetime for the replacement's complete response window.

A false allocation can contain every producer in its admission evidence while omitting another registered producer. A genuine later block from that producer then fails with `issuer has no sealed stake row`. The error identifies the epoch and pool. Verifying a complete alternative table on the same ancestry does not establish misbehaviour and cannot replace the installed allocation. This case requires authorized recovery. It does not have a permissionless challenge-based repair.

The recovery gate opens at `LatestCheckpointTimestamp + TrustingPeriod`. Equality is expired. Unfinished uploads, historical alternatives and failed continuations cannot renew that timestamp. A contiguous canonical update cannot advance its checkpoint through the omitted producer. Even if earlier checkpoints still advance, their expiration is no later than the omitted block's timestamp plus the trusting period. This bounds the wait for recovery eligibility on that ancestry. Recovery also depends on a live destination and its recovery authority. There is no bound on how long governance may take to authorize a request.

Prepare a separately trusted substitute with the complete allocation and the correct nonce, registrations, production, certificate counters and packet state at a newer checkpoint. Its proof-bearing height and Cardano checkpoint must both satisfy the recovery keeper's forward-progress checks. Import it using the bounded bootstrap operations. It must remain active and its checkpoint and proof epoch must already be usable. It needs enough remaining lifetime to complete recovery. Once the subject expires, its recovery authority submits `MsgRecoverClient` naming that subject and substitute. An ordinary signer cannot select a replacement. Afterwards any funded signer can submit `MsgContinueClient` with operation `12` to finish the pinned recovery. Each continuation checks at most 32 retained subject certificate counters, so at most `max(1, ceil(N / 32))` continuations are needed for `N` counters. Counter rollback is rejected. The replacement gets a new verification generation and a commitment cutoff without a twelve-hour wait. Old roots and receipts remain unusable. The connection, channel and pending packet accounting stay attached to the original client identifier.

`TestStakeOmissionExpiresAndRecoversThroughAuthority` runs this sequence through the real v8 and v10 message routers and keepers using signed synthetic Praos history. It admits a twelve-row allocation, then rejects the genuine continuation from its omitted thirteenth producer. A complete observation of the same ancestry cannot freeze or replace it. Recovery is rejected immediately before expiry and for an unauthorized signer. At expiry the authority can pin a trusted substitute. One bounded counter continuation completes this fixture's recovery. After the recovery cutoff has a completed host block the original client verifies the formerly blocked producer while retaining its channel and pending packet records. This is an availability fallback through an explicit trust decision, not authentication of the unsigned allocation or uninterrupted operation.

Client creation uses the ordinary Hermes command. Gateway selects the current indexed Cardano point or the requested height. That point must contain the bridge instance's HostState UTxO. A height before its creation is rejected. Initial creation trusts the operator's configured Cardano node and history providers. It does not require settled descendants or replay bridge updates from before the initial HostState existed.

Gateway reads the initial stake, nonce accumulators, pool registrations, recent production, certificate counters and packet state at that point. Registrations include pools with zero election stake and preserve pending key changes, retirement timing and the frozen mark and effective bindings. Public deployments use their configured pool-history provider when the local index does not contain the earlier certificates. Missing or inconsistent initialization data is an error. Subsequent updates still derive these values from verified block evidence.

Creation also requires Mithril. Gateway passes the aggregator in `MITHRIL_ENDPOINT` to `prepare-client`, which sets the client's anchor for the epoch before the initial point. It adds the certificate of the stake distribution that elects the initial epoch's leaders to the final import, after checking that distribution against the initial stake table. The initial epoch must be at least 3, and Mithril must already have certified that distribution.

The Gateway image includes the native `prepare-client` encoder. Local `npm run build` and `npm test` build it automatically with Go and a C compiler, because Mithril certificate verification uses cgo. It converts the starting state into the small `MsgCreateClient` records and ordered bounded imports. Hermes submits creation and then requests one import at a time through `QueryNewClient`. No operator bootstrap file or `probabilistic_bootstrap_file` setting is required. The configured probabilistic trusting period defaults to at least 48 hours so it exceeds the existing maintenance budget.

Interrupted creation keeps its client identifier. Hermes queries the destination's committed import cursor and requests the next message for that same initial height. It rejects data for another checkpoint. Gateway retains up to 64 unexpired initialization plans in an automatically managed subdirectory of `CONSENSUS_HISTORY_CACHE_DIR`. It removes expired plans when space is needed. At capacity it rejects preparation of another initial point rather than deleting data needed by a pending client. Keep that cache volume across restarts so pending imports can resume after the node has pruned the original ledger point. Each query returns one bounded message instead of the complete snapshot. The initial creation message also commits the ordered import transcript. Imports contain eight pages except for the final batch. Another uploader can relay the exact next operation but cannot reorder authentic pages and move the saved cursor onto a different plan. Smaller nonfinal batches are rejected so another uploader cannot consume the import sequence with valid fragments. Preparation rejects a plan that would exceed the existing 4,096-operation bound before submitting `MsgCreateClient`. The client remains unavailable for proofs while imports are pending. Completion verifies the Mithril certificate against the imported table, so the initial epoch's table needs no response window. Previously exported host deadlines do not carry over.

Pending initialization created with the former manifest must be recreated with this plan commitment. Completed clients keep their existing checkpoint references. The optional `cmd/bootstrap` command remains an offline preparation utility for explicit checkpoint exports and fixtures, and requires `-mithril-aggregator` too. It is not part of ordinary creation. Existing version `0` records remain rejected. Supporting an existing deployment requires a separately audited host migration or new clients and routes.

Gateway uses the historical production and credit context expanded by Hermes from pinned destination queries. It builds the complete logical observation. That off-chain evidence is not an executable client update. Hermes splits that observation into bounded transactions and checks committed transaction errors. Startup monitoring discovers stored future-epoch proposals and retrieves their original checkpoint. It does not substitute the latest client history for the proposal's saved history.
