Five transfers of the same asset on one channel currently spend the same HostState, channel and escrow outputs. Splitting only the host commitment would leave the other shared writes in place.

This branch adds an opt-in native-asset transaction path and tests it through compiled validators. Users independently fund intent outputs. A batch consumes those intents, advances a separate send sequencer, inserts packet commitments into the affected lanes and creates one liquidity output per deposit. Channel configuration, connection and client state are reference inputs. Sending the next included batch does not depend on acknowledgements. The live Gateway and existing deployed validators still use the singleton path. This branch does not yet fix production transfer latency.

`packet_lanes.ak`, `packet-lanes.ts` and `packet_lanes.go` assign `sequence % lane_count`. Every consecutive window of at most `lane_count` sends occupies distinct lanes, including wraparound. Older outstanding packets can still share a lane with new packets. The builder groups mutations by lane and computes each witness against the preceding mutation's root. Separate transactions that lose a competing spend must rebuild from included state. Lane assignment is a breaking change from the earlier hash-based prototype. Token identities still use domain-separated hashes and the lane count must remain fixed for a channel.

`packet_lane_batch.ak` authenticates funded native deposits, successful acknowledgement proofs and timestamp timeout proofs for unordered transfer channels. `packet_lane_guard.ak` binds intent, sequencer and lane spends to that operation. Intent owners can cancel unspent intents with their payment-key signature. The existing state-transition helper checks identity tokens, unique continuations and exact lane state and root changes. Successful acknowledgements remove commitments without spending liquidity. Timeouts authenticate remote receipt absence and bind the released principal to a tagged payment to the packet sender. This path currently accepts proofs at the referenced client's latest checkpoint. Voucher burns, receiving packets, error acknowledgements, ordered channels and older consensus-history witnesses still need integration.

Liquidity identities include the consumed deposit reference. A full drain burns the identity and returns the entire ADA reserve to the immutable reserve owner. Each reimbursement has a distinct identity tag so one output cannot satisfy several refunds. For newly funded intents the owner is the depositor's payment key at its enterprise address. The batcher supplies fees separately. Empty outputs can retire without a packet proof. Nonempty outputs require an authenticated timeout refund or consolidation that preserves all principal. Consolidation keeps one identity and its reserve while burning the others and reimbursing their owners. The timeout builder currently selects complete deposits whose combined principal exactly covers the refund.

The transaction builder caps sends at two intents. In the empty-lane fixture a two-intent transaction is about 7.4 KB and uses 15.8 million memory units and 4.8 billion CPU units. Acknowledgements use about 3.9 KB and 5.4 million memory units. These are measured examples under the checked-in limits of 16,384 bytes, 16.5 million memory units and 10 billion CPU units. They are not capacity guarantees for larger packet data or populated lanes. Every completed transaction still needs evaluation and ledger-limit checks. The sequencing primitive's five-packet bound is not a five-packet capacity claim.

Run `aiken build` in `cardano/onchain` before `deno task test:packet-lanes` in `cardano/offchain`. The tests admit five separately funded requests before any acknowledgement, send them in batches of two, two and one, and submit five independently built acknowledgement transactions. They also exercise same-lane sequential witnesses, stale spends, competing batch builders, rollback, consolidation and full-drain timeout refunds. They seed authenticated channel, client and lane pre-state. They do not execute deployment or remote client updates. The timeout test supplies a later authenticated checkpoint as fixture state. Script evaluation uses the supported first 297 entries of the pinned 350-entry V3 cost model because `@lucid-evolution/uplc` version `0.2.23` mishandles the longer model. Those entries retain the ledger costs for the builtins used here. Transaction construction uses the complete model. These emulator results still need a node-backed integration run.

The Go extractor authenticates an output's lane identity within a caller-authenticated settled anchor block. It derives the proof height from that block and rejects outputs spent later in the block. It does not carry roots forward. The consensus-state adapters must track each lane's live output and process a complete authenticated sequence of intervening blocks before reusing an unchanged root at a later height. Missing block coverage, competing successors and rollback must invalidate the newer snapshot. An old empty root cannot simply be labelled with a timeout's later proof height. That integration remains unfinished.

Deployment also needs unique lane and sequencer identity issuance and an exclusive handover from legacy packet state. Running both paths for one channel would create separate send counters and packet histories. Do not enable this path on a live channel before that handover is enforced. Gateway routing, per-lane indexing and counterparty consensus storage remain required. The existing Gateway already returns an unsigned send transaction without waiting for acknowledgement. Hermes waits for the Gateway's accepted height before advancing its message loop. A complete-transfer duration alone does not establish that each local spend waits a settlement window.
