Five transfers of the same asset on one channel used to share the HostState, channel and escrow outputs. This branch makes packet lanes the default transfer path in fresh deployments. It changes the validators, Gateway, Hermes relayer and both probabilistic light-client adapters. There is no switch that enables the old transfer packet path alongside it. Existing deployments and active channels are not migrated by changing a manifest. Deploy fresh contracts and update the partner chain's light-client binary before testing.

Each user first funds an independent intent output. Hermes admits all transfers in an all-transfer request before building send batches. The Gateway validates pending intents individually and advances past temporarily unusable requests. Packet builds reserve their lane, fee and collateral inputs within the Gateway until canonical consumption or ledger-time expiry. The relayer wallet needs multiple funded outputs for concurrent packet transactions. The Gateway batches at most two intents into a transaction that escrows or burns their funds, assigns consecutive sequences and writes packet commitments. A separate send sequencer preserves IBC v1's channel-wide counter. The next batch builds on included state without waiting for acknowledgements or a settlement window. Competing builders reload spent inputs and retry. Included intent spends are recovered through canonical history after an ambiguous submission. Counterparty proofs still require settlement evidence.

The dapp user signs one funding transaction. `buildUnsignedTransfer()` now creates that intent and does not construct a HostState update. When Hermes starts its Cardano event subscription it also starts a background executor. The executor discovers funded requests across transfer channels, initializes lanes when needed and signs bounded batches with the configured relayer wallet. That wallet pays batch fees under the existing signing policy and trusted-node evaluation limits. Successful inclusion triggers the next executor pass immediately. Idle periods and failed channels retain backoff. Keep it funded. Closing the browser does not stop execution. An unavailable relayer leaves the request funded until service resumes or the owner cancels it.

The UI reads canonical intent status without any batch-building or signing endpoint. It distinguishes request funding, packet inclusion and successful destination receipt. Packet events bind each intent to its assigned sequence so a request cannot display another packet's progress from the same batch. Refreshes retain the request identifier. Rollbacks return tracking to the current funded state and the executor rebuilds from current inputs.


Packet assignment is `sequence % lane_count`. Fresh deployments use 16 lanes. Consecutive sequences use different lanes until wraparound. Older packets can share a lane with new packets, so the batch builder groups mutations by lane and supplies sequential witnesses. Lane identity issuance is authenticated by a channel registry used only during initialization. Ordinary packet transactions read HostState control, channel, connection and client outputs as references. They do not spend HostState, the channel output or an aggregate packet-root output. Updating a referenced dependency can still invalidate a pending transaction.

Small operation policies authorize packet actions. A spending guard checks exact lane continuations and roots. Separate policies verify ICS-23 proofs and conservation of funds. They read one batch authorization so large lane witnesses are not copied into several redeemers. Each applied script is published in its own reference output when needed. The immutable deployment configuration pins the registry used for first-time voucher registration.

The default path supports unordered ICS-20 sends with timestamp timeouts, receives, successful and error acknowledgements, timeouts, timeout-on-close and receipt pruning. Proofs can use older Tendermint consensus checkpoints through authenticated history witnesses. Each native deposit has a separate liquidity identity. Releases may partially spend a deposit or fully drain it and burn its identity. Full drains return the reserve to the depositor's enterprise address using a distinct reimbursement tag. Consolidation preserves principal and returns retired reserves. Voucher receipts authenticate denomination metadata and first-time registry writes. Returning vouchers burn through the same deployed voucher policy. Intent owners can cancel unspent requests.

Liquidity discovery authenticates the complete datum, its derived identity NFT and the principal and ADA reserve before selecting inputs. Malformed or counterfeit outputs at the same script address are ignored individually.

Accounting is separate from packet history. Each lane has at most eight accounting entries keyed by the 32-byte SHA-256 hash of the full denomination. Pruning a receipt does not erase an asset obligation. The Gateway's `ibc.cardano.v1.CardanoMsg/CompactPacketBalances` RPC builds a maintenance transaction for `left_lane` and `right_lane` on a transfer channel. It cancels opposite balances and redistributes the remaining entries. Optional `left_denoms` places specific full denominations in the left lane, which lets an operator make room for a return between settled lanes even when both maps are full. The transaction preserves both packet roots, replay state and ADA reserves. The validators require the same per-asset total and forbid creating additional offsetting debt or splitting an obligation across more lanes. Maintenance requires exactly two state-token inputs so a negative balance cannot cancel obligations in overlapping pairs. Neither lane may have outstanding sends. Maintenance cannot be combined with a packet operation. No global state is spent.

A lane retains zero-balance entries while it has outstanding sends. These entries reserve capacity for refunds and count toward the eight-entry limit. The last acknowledgement or refund removes unused zero entries. This conservatively holds reservations for the whole lane until every outgoing packet settles.

Operators must compact completed cross-lane round trips before the maps fill. A full map rejects new asset entries with an explicit capacity error. Maintenance reloads current lane outputs and must be rebuilt after a competing spend or rollback. The two-lane capacity test sends and acknowledges 24 distinct native assets, returns each through a different lane and prunes every receipt. It fills both eight-entry maps and compacts them three times using signed transactions under the pinned ledger limits. A separate full-channel fixture fills all 128 slots, burns a voucher balance and rejects attempts to reuse its reserved slot. Both timeout and error-acknowledgement refunds restore the voucher at full capacity.

The partner client stores authenticated lane snapshots with each accepted consensus state and retains checkpoint cursors needed for later updates. Every bridge block and anchor includes its complete body. The client checks body hashes and continuity, tracks consumed lane outputs and accepts only their authenticated continuations. It carries an untouched root forward only after processing all intervening bodies. Settlement descendants can use compact headers because their state lies after the anchor. This increases checkpoint payload sizes. Missing bodies, skipped lane changes and competing continuations fail verification. Gateway packet proofs use the root at the requested settled height and detect rollbacks during construction. Non-packet proofs use the HostState root carried to that height.

Run `aiken build --deny --trace-level silent` in `cardano/onchain`, then `deno task test:packet-lanes` in `cardano/offchain`. The compiled transaction tests fund five independent intents, send batches of two, two and one before acknowledgements, then build five acknowledgement transactions before submitting any of them. They also cover same-lane witnesses, stale spends, competing builders, rollback, partial and full releases, consolidation, voucher receipt and burn, pruning, historical proofs and timeout-on-close. CI runs this suite. The deployment suite checks that every applied reference script fits its signed publication transaction. Gateway and Go tests share a snapshot encoding fixture.

For node evaluation, run `PACKET_LANE_NODE_URL=http://localhost:2637 deno test --allow-env --allow-read --allow-net src/packet-lane-transactions.test.ts`. The fixture asks Ogmios for current chain timing and evaluates real signed transactions with additional fixture UTxOs. Local tests use the Scalus evaluator with the full pinned V3 cost model. Node evaluation uses the node's full cost model. The optimized local 64-request run kept two-intent batches around 8 KB and at most 15.07 million memory units under the 16 KB and 16.5 million limits. A first-time voucher receipt with a short denomination and empty registry shard measured about 8.3 KB and 13.8 million memory units. That leaves about 8.7% memory headroom in this fixed workload. They do not establish capacity for maximum-size packets, full lanes or heavily populated registry shards. Every Gateway transaction is evaluated before signing and the batch builder falls back to one intent if two do not fit.

These tests establish compiled transaction behavior and node execution budgets with authenticated fixture pre-state. They do not submit fixture transactions to the live node or execute a transfer across two running chains. A fresh deployment and partner-chain run are still needed to measure wall-clock latency. The expected improvement is overlapping settlement windows for different packets, while preserving the short send-sequencer dependency.

Shutdown blocks new escrow deposits and voucher receipts while allowing returns and existing packets to settle. Voucher metadata and trace state remain available until every channel has drained. Each lane tracks its local asset obligations. Retirement authenticates all lanes and requires no commitments and zero total obligations before burning the send sequencer. It then retires one lane per transaction with an authenticated progress certificate. Channel cleanup requires the completed certificate. Configuration, registry, certificates and published references are reclaimed after the channels. The shutdown suite exercises timeout refunds, error acknowledgements, returning escrow and final ADA recovery through the deployed lane validators.
