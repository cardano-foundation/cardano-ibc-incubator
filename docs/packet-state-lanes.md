Five transfers of the same asset on one channel currently spend the same HostState, channel and escrow outputs. Splitting only the HostState root would leave the other two dependencies in place.

The `feat/407-packet-state-lanes` branch currently contains protocol primitives. It does not yet implement issue #407 end to end. The running Gateway and deployed validators still use the existing singleton state. The new Aiken functions are library functions rather than deployed validators. Their callers must authenticate channel configuration, application callbacks, packet proofs and intent funding. In particular, a successful lane transition or liquidity accounting check alone does not authorize a packet or a withdrawal.

`packet_lanes.ak`, `packet-lanes.ts` and `packet_lanes.go` agree on lane assignment. The preimage is the UTF-8 domain `cardano-ibc/packet-lane/v1`, a zero byte, the port and channel each prefixed by a four-byte big-endian length, and an eight-byte big-endian packet sequence. The first eight bytes of SHA-256 are interpreted as an unsigned big-endian integer and reduced modulo the fixed lane count. Commitment, receipt and acknowledgement keys for the same local packet sequence share one lane. Channel and sequence identifiers must have their canonical decimal spelling. The lane count must remain fixed for a channel.

The unordered lane datum holds packet maps, a root, a version and receive-proof pruning bounds. Each mutation checks the key assignment and exact sparse-tree update. The state-thread helper checks the identity token and unique successor. The separate send sequencer accepts consecutive sequences in batches of up to five. This is a bound on the primitive, not a measured transaction-capacity guarantee. Ordered receive and acknowledgement counters still need their own serialized protocol path.

Liquidity identities include the consumed deposit reference as well as the port, channel and denomination. Accounting helpers preserve each output's identity and ADA reserve. They allow several independently authenticated balances to fund one release. The minting policy and transfer operation must still bind deposits and releases to funded intents, voucher burns and recipient payments.

The Go extractor checks a lane NFT in a phase-2-valid transaction within an anchor block. It derives the proof height from that block and rejects an output spent later in the same block. Its caller must first authenticate and settle the block and supply trusted lane policy and partition parameters. Proof helpers enforce the packet key's lane and exact height. These helpers are not yet connected to the light-client consensus-state adapters.

The existing Gateway send builder returns an unsigned transaction without waiting for acknowledgement. The standalone runtime returns after Ogmios submission. Hermes does wait for the Gateway's accepted height in `sign_submit_and_wait`, and its message loop awaits that helper before proceeding. Completing the implementation requires independently funded intent admission, atomic batch construction, lane and sequencer identity issuance, application and proof authorization, per-lane indexing, light-client consensus storage, and a submission path that handles inclusion and rollback separately from counterparty settlement.

Current tests exercise the primitives and five disjoint lane input references. They do not establish the requested acceptance test. That test must submit five funded requests on one channel without waiting for prior acknowledgements, process packets in different lanes independently through actual validators, reject competing spends of the same lane and recover from rollback without publishing unconfirmed roots.
