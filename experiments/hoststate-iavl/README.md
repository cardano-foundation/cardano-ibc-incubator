This branch compares two replacements for the residual 64-bit HostState routing limit in issue #482. The measurements favor keeping the outer tree and resolving collisions inside its leaves. An IAVL migration works algorithmically, but its additional execution cost is difficult to fit into the current packet transactions. This experiment does not switch the production commitment scheme.

The baseline is `main` at `94db12d0644294bb0ac8f09ede920a1980c5bc6a`. Both candidates have executable Aiken update verifiers. The IAVL model is checked against Cosmos IAVL v1.2.2, including roots after rebalancing and multiple writes in one version. The bucket model is independently rebuilt from its entries for every fixture. Results are in `results.json`. The compiler is Aiken v1.1.21 with stdlib 3.1.0. The signed transaction harness uses the same Lucid and ledger capacity settings as the repository's production budget fixtures.

Compression means an eight-byte bitmap identifies nonempty outer siblings. Only those sibling hashes are serialized. It does not change the tree root or remove the 64 hash levels. The cost comparison also includes uncompressed buckets in `results.json`, so the benefits of collision handling and compression can be separated. Ordinary bucket updates hash the key once and reuse its route, which explains why some uncompressed bucket measurements are slightly cheaper than the current implementation despite doing extra checks.

The corresponding compiled batch harnesses are 905 bytes for the current tree, 2,758 bytes for IAVL and 2,540 bytes for compressed buckets. These are isolated scripts. Their differences must not be added mechanically to the production HostState script size because Aiken shares and specializes code differently in that larger validator. Both candidates need an integrated reference-publication size check before deployment.

The main comparison seeds the IAVL tree at version 1, which is optimistic for a long-running deployment. An additional 65,536-key fixture uses node versions above one million. Its isolated insert costs 3,073,823 memory units instead of 2,747,392. Its update costs 2,794,979 instead of 2,474,632 because metadata varints are longer. This strengthens the execution-cost concern.

IAVL would need further optimization or a different update-proof design before the current send and open-try flows could reasonably fit. Buckets leave only about 299,000 projected memory units spare in the send case, so they also need a real integrated budget test. Neither prototype is a production deployment approval. The smaller signed sizes and fees above belong to the isolated harnesses, not complete IBC transactions.

For the IAVL design, store entries are ordered by their full UTF-8 key bytes. Leaves commit to the original key, the value hash and the node version using the exact Cosmos IAVL encoding. Inner nodes commit to height, leaf count, version and child hashes. The empty root becomes SHA-256 of empty bytes instead of 32 zero bytes. Each HostState transaction uses its output `state.version` for every node it creates. All key changes execute in the order already fixed by the HostState validator. Heartbeats and other transitions with no tree changes still advance the offchain store version. All side effects are published only after that exact HostState successor is confirmed.

The IAVL update witness is a partial old tree plus the target leaf's rank. An untouched subtree exposes its authenticated header and child hashes. The verifier reconstructs the old root, derives subtree sizes from authenticated data, checks the old key and value, and performs the insertion, replacement or deletion and any required rotations. Insertions prove the immediate successor as well as the predecessor. Below the minimum key they prove the first leaf. This is necessary because Cosmos IAVL does not hash the inner separator keys. Trusting a supplied separator would allow an invalid search path. Accepting either neighbor as the insertion location would also permit different tree shapes, so the prototype enforces the canonical predecessor position.

The verifier calculates height, size and hash caches itself. Those caches are never trusted witness fields. Without caching and the rank-based witness, the first correct prototype exceeded the transaction memory budget at only a few thousand keys. The current implementation matches the upstream roots after 3,000 mixed insert, overwrite and delete operations. Another 159 generated Aiken update vectors cover rotations, mixed histories and balanced trees through 65,536 entries. Ordinary IAVL membership and neighbor-based absence proofs verify with the upstream ICS-23 library. A sampled membership proof at 65,536 entries is 791 protobuf bytes and a two-neighbor absence proof is 1,617 bytes. These are query proofs, not update witnesses.

An IAVL Gateway must persist the tree topology and every retained node version. A complete current key/value set does not determine the root. The tests demonstrate different roots for the same entries inserted in different orders and with different version boundaries. Exact replay reproduces the root. An upstream full-node export/import also reproduces the root and the next update. A production snapshot must include that structure, versions, the HostState output reference and its authenticated root. Import it into a disposable store, check the root and only then make it current. Rollback must restore the tree version associated with the surviving HostState predecessor and discard speculative descendants. Gateway recovery must replay the exact per-transaction write order, including version increments with no writes. Existing consensus-history recovery supplies relevant infrastructure, but its current key/value cache is not a drop-in IAVL snapshot.

For the alternative design, the outer 64-bit route and its hashes remain unchanged. An empty bucket remains zero. A singleton bucket retains today's `sha256(0x00 || sha256(key) || sha256(value))` leaf. Two keys with the same route create a Patricia subtree over the remaining 192 bits of their SHA-256 digests. A Patricia tree stores branches only at bits that distinguish entries. Its branch hash is `sha256(0x02 || bit_index_byte || left_hash || right_hash)`. The separate tag distinguishes bucket branches from leaves and outer nodes. Branch positions increase from root to leaf and are bounded by the digest length. No version or insertion order enters the commitment.

An existing-key witness carries the bucket siblings and outer siblings. The validator already knows the old key and value from the authenticated transaction, so that leaf does not need to be repeated. An absent-key witness either shows an empty outer position or reveals the different occupied leaf reached by the requested digest. The verifier checks its route and every branch direction. Insertion branches at the first differing digest bit. Deletion collapses the now-unary branch, so deleting one of two colliding keys restores exactly the original singleton format. Canonical bitmap encoding rejects missing siblings, extra siblings, explicit zero siblings and bits beyond level 63. Membership uses the same authenticated path. Absence inside an occupied bucket must reveal the different terminal leaf, it cannot reuse today's empty-value proof.

This resolves the truncated-route problem while retaining the usual full SHA-256 security assumption. It is not a mechanism for distinguishing two keys whose entire SHA-256 digests collide. Today's key-bound leaves already rely on that full digest. Test fixtures force matching 64-bit prefixes to exercise the resolver. They are not discovered SHA-256 collisions. Fixtures include coexistence, updates, deletion, exclusion, a split at the last digest bit and a structural extreme with all 192 bucket levels occupied. In that extreme, a single update uses 8,948,315 memory units before compressed-witness decoding and carries a 9,843-byte uncompressed witness. Two such paths need shared proofs or another strategy to fit a transaction. There is no claim that every pathological state supports every multi-key operation within fixed ledger limits.

For ordinary random digests a two-entry collision bucket adds one branch. Larger bucket tests cover 8 and 64 entries. The outer bitmap is useful even when there are no collisions. At 65,536 keys the four-insert bucket witness payload is 2,220 bytes compared with 5,794 for IAVL and 8,714 for the current tree. These payload sizes exclude keys and values already available to the production validator. The signed harness includes them so that its standalone scripts have all the required inputs.

Bucket reconstruction remains a function of the complete current committed key/value set. That set may already require authenticated history to recover retained consensus entries, but it does not additionally require the historical mutation order and node versions. The in-memory and SQLite implementations must allow several full keys at one route and persist or deterministically rebuild the Patricia nodes. The SQLite `UNIQUE(path)` constraint must be removed. A disposable cache schema version must reject old incompatible cache layouts. Speculative clones, confirmation, rollback and root checks retain their existing semantics. No bucket-size cap should silently reintroduce the same liveness ceiling.

The production work spans the same boundaries for both choices. Replace `ibc_state_commitment.apply_update` and the HostState redeemer witness types. Update all Aiken, TypeScript and Plutus encodings together. Replace `ICS23MerkleTree`, `IncrementalIbcTree` and the transaction-builder interfaces that currently call `getSiblings`. Update the Gateway's membership and absence queries. Change both the shared probabilistic verifier and the Mithril verifier, then test the v8 and v10 adapters against the same vectors. The existing CBOR-to-IBC value comparisons remain necessary whichever tree is chosen. Shared uses of the current Merkle helper, including escrow registries, must be given an explicit scheme rather than silently changing their roots along with HostState.

IAVL queries can carry standard IAVL ICS-23 proofs. Bucket queries need an explicit proof envelope for the outer bitmap, bucket branch indices and optional different occupant. The maintained Cosmos verifiers must validate this structure rather than passing the current placeholder leaf operations to a generic verifier. Both schemes need an explicit commitment-scheme identifier bound to the deployment and retained with trusted consensus roots. `HostState.state.version` remains a transition counter, not a scheme selector. Reject mismatched schemes and malformed encodings before root comparison. Retain the appropriate verifier for historical roots across an upgrade.

An IAVL migration changes every nonempty root and the empty root. It therefore needs a fresh deployment or a separately specified authenticated state-conversion procedure. The existing state-preserving redeployment flow cannot simply substitute a different root. For buckets, every state reachable under the old collision-rejecting tree consists of empty or singleton buckets, so its root is preserved. That makes the existing authenticated redeployment mechanism a possible migration route once new scripts, witnesses and counterparty verification are coordinated. It still does not allow changing already deployed validators without an upgrade.

The recommendation from these measurements is to pursue compressed Patricia buckets first if the objective is resolving #482 with the least disruption. IAVL becomes more attractive if standard Cosmos proofs and its mature storage implementation justify the recovery changes, or if a shared multi-key IAVL witness materially reduces execution cost. Neither prototype implements shared multi-key proofs. A production choice should next require integrated send, receive, channel creation, timeout, pruning and recovery tests, reference-script publication checks, rollback tests and a published supported state-size and collision-path envelope. The scarce resource in the current send fixture is execution memory, not proof bytes.

Validation completed with 396 passing Aiken tests, four Go design tests, 3,000 upstream differential operations, 12 signed kernel transactions and three unchanged production transactions. Go vet and Deno type checking also passed.

Run `./run.sh` from this directory with Go 1.23 or newer, Aiken v1.1.21 and Deno installed. It regenerates fixtures, checks the upstream model, runs Aiken tests, builds the benchmark-only validators, evaluates signed transactions and writes `results.json`. Run `./run-production-baseline.sh` to rebuild and measure the three unchanged production fixtures. Generated witness files and raw logs are under ignored paths. The benchmark validators accept roots from redeemers purely to isolate costs and must never be deployed as HostState validators.
